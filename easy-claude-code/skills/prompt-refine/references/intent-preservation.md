# 의도 보존 불변량 (Intent Preservation Invariants)

이 문서는 `prompt-refine` 스킬이 프롬프트를 개선할 때 **절대 변경하면 안 되는 요소**와, 변경이 필요한 경우 **반드시 사용자에게 확인**해야 하는 요소를 정의한다. 단어 하나가 요청의 의미를 바꾸는 도메인 특성상, 이 불변량은 개선 품질보다 우선한다.

---

## 핵심 원칙

**"의미 동치 재표현"과 "의미 변경"의 경계가 조금이라도 모호하면, 변경하지 말고 확인한다.**

프롬프트 개선의 목적은 "같은 의도를 더 명확하게 전달"하는 것이지, "내가 추측한 더 나은 의도"로 바꾸는 것이 아니다. 개선자는 원저자가 아니다.

**판단 기준**: "원저자가 이 개선본을 보고 '내가 의도한 그대로다'라고 말할 수 있는가?" 그렇다면 진행, 아니라면 확인.

---

## 불변 요소 6종

### 1. 고유명사·브랜드·제품명

**규칙**: 원형 유지. 동의어 치환 금지. 축약·확장 금지.

**사례**:
- `황금거위` → `황금 거위` ❌ (공백 추가 금지)
- `황금거위` → `Golden Goose` ❌ (번역 금지)
- `Supabase` → `Supa Base` ❌ (공백 추가 금지)
- `AdMob` → `Admob` ❌ (대소문자 변경 금지)
- `GoldenGoose` → `황금거위` ❌ (원문 언어가 영어였다면 영어 유지)

**예외**: 명백한 오타(예: `Suupabase` → `Supabase`)는 수정 가능. 단, 도메인 확인이 필요하면 AskUserQuestion 트리거.

### 2. 기술 식별자 (파일 경로, 함수명, @mention, URL)

**규칙**: 텍스트로만 취급. 변경·접근·정규화 금지.

**사례**:
- `@v2/` → `@v2` ❌ (경로 끝 슬래시 제거 금지)
- `/api/v1/users` → `/api/users` ❌ (버전 생략 금지)
- `fn_credit_point` → `credit_point` ❌ (prefix 제거 금지)
- `build_runner.dart` → `buildRunner.dart` ❌ (네이밍 컨벤션 변경 금지)
- `https://foo.com/a` → `https://foo.com/a/` ❌ (trailing slash 추가 금지)
- `--flavor development` → `-flavor development` ❌ (옵션 플래그 축약 금지)

**이유**: 이 식별자들은 실제 시스템의 존재를 가리킨다. 한 글자만 달라져도 다른 대상이 된다. 맞춤법 교정 대상이 아니다.

### 3. 숫자·단위·시각

**규칙**: 변경 시 **필수 확인**. 반올림·근사 금지.

**사례**:
- `3회` → `세 번` ❌ (단위·표기 변경 금지, "3회"는 정확한 횟수)
- `09시` → `9시` ❌ (표기 형식이 도메인 관습일 수 있음)
- `KST 09:00` → `오전 9시` ❌ (타임존 삭제 금지)
- `3-5개` → `약 4개` ❌ (범위를 값으로 압축 금지)
- `50%` → `절반` ❌ (수치 → 자연어 치환 금지)
- `30분` → `반시간` ❌

**모호한 수량에서 확인 필요**:
- 입력이 `"대략 10번 정도"`라면: "10번 정확히"인지 "10±2" 범위인지 확인.
- 입력이 `"많이"`, `"충분히"`, `"몇 개"`라면: 구체 수치가 필요한지, 의도적으로 모호하게 둘지 확인.

### 4. 도메인 용어

**규칙**: 동의어 치환 금지. 프로젝트·업계 전용 용어는 원형 유지.

**Golden Goose 도메인 사례**:
- `알` → `달걀`, `난자`, `egg` ❌
- `오퍼월` → `광고 벽`, `offerwall` ❌
- `오퍼월` → `오퍼형` ❌ **(한 글자만 바뀌어도 다른 용어가 됨 — 실제 벤치마크에서 발생한 실패 사례)**
- `메인배너` → `메인 배너`, `메인 베너` ❌ (공백·철자 변경 금지)
- `출금` → `송금`, `환전` ❌ (서비스 내 구분 있음)
- `포인트` → `리워드`, `점수` ❌ (명확한 도메인 용어)
- `응모권` → `티켓`, `이용권` ❌
- `이벤트 응모권` → `응모권` ❌ (축약 금지, 전체 용어)
- `보상형` → `리워드형`, `Rewarded` ❌

**특히 주의 — 반사적 "비슷한 글자" 변형**: 도메인 용어를 여러 번 쓰다 보면 무의식적으로 비슷한 글자로 바꾸는 오기가 발생한다 (예: 동일 프롬프트 내에서 `오퍼월`을 5번 쓰다가 1번 `오퍼형`으로 쓰는 경우). **변환 직후 원문과 출력의 도메인 용어를 1:1 비교 검증**하여 모든 출현 위치에서 철자가 일치하는지 확인할 것.

**일반 기술 도메인 사례**:
- `PR` → `Pull Request`, `풀 리퀘스트` ❌ (원문 유지)
- `JWT` → `JSON Web Token` ❌ (약어가 원문이면 약어 유지)
- `Edge Function` → `엣지 함수`, `서버리스 함수` ❌
- `Clean Architecture` → `클린 아키텍처` ❌

**예외**: 프롬프트가 명시적으로 "용어 설명을 추가하라"고 요청하면, 원문을 유지하면서 괄호 안에 설명 추가 가능 (예: `알(Golden Egg)`).

### 5. 제약·조건·부정 표현

**규칙**: 의미 동치 재표현만 허용. 삭제·약화·강화 금지.

**허용되는 재표현**:
- `~는 하지 않는다` ↔ `~는 금지한다` ✅
- `만약 A이면 B` ↔ `A인 경우 B` ✅
- `반드시 ~해야 한다` ↔ `~는 필수다` ✅
- `A하지 마, B하지 마, C하지 마` ↔ `A/B/C를 피한다` ✅ (중복 제거, 의미 동치)

**금지되는 변경**:
- `하지 않는다` → `권장하지 않는다` ❌ (강한 금지 → 약한 권고)
- `반드시` → `가능하면` ❌ (필수 → 선택)
- `오직 X만` → `주로 X` ❌ (배타적 → 우선적)
- `모든 경우` → `대부분의 경우` ❌ (전체 → 부분)
- `1회만 허용` → `최대 1회` ❌ ("허용"과 "최대"는 다른 의미)
- 제약 자체 삭제 ❌ (예: "간결하되 500자 이내"의 "500자" 삭제)

### 6. 플레이스홀더·변수

**규칙**: 원형 유지 (기존 스킬 규칙과 동일).

**사례**:
- `{user_name}` → `사용자명` ❌ (실제 값으로 채우지 않음)
- `{{date}}` → `{date}` ❌ (중괄호 개수 변경 금지)
- `[TOPIC]` → `[주제]` ❌ (대괄호 내부 식별자 번역 금지)
- `$VAR` → `$var` ❌ (대소문자 변경 금지)
- `<<<INPUT>>>` → `<INPUT>` ❌ (구분자 개수 변경 금지)

**이유**: 플레이스홀더는 템플릿 엔진이 인식하는 정확한 문자열이다.

## AskUserQuestion 트리거 기준

아래 중 **하나라도** 해당하고, 합리적 기본값 추정이 요청의 본질을 바꿀 수 있을 때 AskUserQuestion을 호출한다. 여러 개가 동시에 해당하면 1회 호출 안에 최대 3개 질문을 묶는다.

1. **숫자·수량 변경이 필요해 보임** — 원문이 모호한 수량("많이", "몇 개")을 담고 있어 구체화가 요청의 핵심에 영향을 줄 때.
2. **대명사 참조가 불명** — "이것", "그 기능" 등이 무엇을 가리키는지 2개 이상 후보가 있을 때.
3. **동음이의어** — 도메인 용어의 의미가 문맥상 2개 이상일 때 (예: "포인트"가 리워드인지 UI 좌표인지).
4. **대상 불분명** — "사용자"가 관리자/일반 유저/비회원 중 누구인지 확정 불가.
5. **실행 환경 불명** — 모바일/웹/CLI/서버 어느 컨텍스트인지 결과물 형태에 영향.
6. **출력 형식 후보 다수** — 리스트/표/문장/JSON 중 확정 필요하지만 원문에 단서가 부족.

**트리거하지 않는 경우**:
- 단순 문법 개선, 어휘 명확화로 해결 가능.
- 복잡도가 단순하고 의도가 투명하게 드러남.
- 모호성이 있어도 업계 관행상 명확한 기본값이 있고, 개선본에서 그 기본값을 명시적으로 드러낼 수 있음.

---

## 확인 없이 해도 되는 개선

다음은 의미 변경이 **아니므로** 확인 없이 적용 가능하다:

- 동일 의미의 더 명확한 동의어 (일반 어휘에 한해) — 예: `글자` → `문자`
- 문장 구조 재배열 (주어·목적어 명시화)
- 마크다운 포맷 추가 (제목, 목록, 강조)
- XML 태그 분리 (`<context>`, `<instructions>` 등)
- 중복 지시 통합 (같은 의미 반복을 하나로)
- 수동태 → 능동태 전환
- 암묵적 정보의 명시화 (단, 원문에 근거가 있을 때만)
- 단순 오타 교정 (단, 고유명사·기술 식별자는 제외)

## Before/After: 의도 보존 실패 사례

### 사례 1: 도메인 용어 치환 실패

```
[원문]
알을 하루에 3회 지급하는 기능을 추가하는 프롬프트 작성해줘.

[잘못된 개선]
달걀을 하루에 3번 지급하는 기능을 추가하는 프롬프트를 작성한다.
→ "알"을 "달걀"로 바꾸면 Golden Goose의 도메인 용어에서 이탈. 앱의 핵심 개념이 다른 의미로 해석될 수 있음.

[올바른 개선]
<task>하루 3회 자동으로 "알"을 지급하는 기능에 대한 프롬프트를 작성한다.</task>
<context>사용자는 알을 열어 포인트를 획득한다.</context>
<output_format>지시문 형태, 5-10줄 이내.</output_format>
```

### 사례 2: 수치 근사 실패

```
[원문]
응답 시간을 50% 단축하는 최적화 프롬프트 개선해줘.

[잘못된 개선]
응답 시간을 절반으로 줄이는 최적화 프롬프트를 작성한다.
→ "50%"와 "절반"은 대부분 동의어지만, 성능 목표 명세에서는 정확한 수치가 요구됨. 49.9%는 절반이 아닐 수 있음.

[올바른 개선]
응답 시간을 기존 대비 50% 단축하는 최적화를 수행한다. 측정 방법: P95 응답 시간 기준.
(수치 원형 유지, 측정 기준만 명시화)
```

### 사례 3: 제약 강도 변경 실패

```
[원문]
외부 라이브러리는 반드시 허용 목록에 있어야 한다.

[잘못된 개선]
외부 라이브러리는 가능하면 허용 목록에 있는 것을 사용한다.
→ "반드시"를 "가능하면"으로 약화. 보안·규정 컨텍스트에서는 치명적 의미 변경.

[올바른 개선]
외부 라이브러리는 허용 목록에 등재된 것만 사용한다.
(재표현은 되었으나 "만" = "반드시 그것에 한정"의 의미 동치 유지)
```
