# 프롬프트 안티패턴 심화 가이드

이 문서는 `prompt-refine` 스킬이 감지·교정해야 할 8가지 안티패턴을 Before/After 예시와 교정 원리와 함께 설명한다. SKILL.md 본문의 안티패턴 표는 이 문서의 요약이며, 실제 교정 판단은 이곳을 참조한다.

---

## AP-1: 모순 지시 (Contradictory Instructions)

### 왜 나쁜가
서로 충족할 수 없는 두 조건을 동시에 요구하면 모델은 임의 선택을 하게 되고, 결과가 일관되지 않는다. 사용자가 실제로 원한 것은 둘 중 하나이거나, 둘 사이의 트레이드오프에 대한 명확한 우선순위다.

### Before
```
간결하되 모든 세부사항을 빠짐없이 포함해서 답해줘.
```

### After (우선순위 명시)
```
간결성 > 완전성 순으로 우선시한다.
- 먼저 핵심을 3-5문장으로 답한다.
- 이후 "세부사항" 섹션에서 보충 정보를 제공한다.
```

### After (조건부 분기)
```
독자 수준에 따라 분기한다:
- 입문자: 간결하게 3문장 이내
- 전문가: 세부 구현까지 포함
```

### 교정 원리
두 지시가 충돌할 때는 (1) 우선순위 명시, (2) 조건부 분기, (3) 두 단계 분리 (개요 → 상세) 중 하나를 선택한다.

## AP-2: 중복 강조 (Redundant Emphasis)

### 왜 나쁜가
같은 지시를 여러 번 반복하면 토큰을 낭비할 뿐 아니라, 모델이 "왜 이게 반복되지? 뭔가 특별한 의미가 있나?"라고 해석해 불필요한 우회 행동을 할 수 있다. 한 번, 가장 명확하게 말하는 것이 강력하다.

### Before
```
반드시 한국어로 답해줘. 한국어로 응답하는 게 중요해. 답변은 무조건 한국어여야 해. 영어는 쓰지 마.
```

### After
```
답변 언어: 한국어 (영어 단어 필요 시 괄호 병기 허용).
```

### 교정 원리
같은 지시를 반복한 경우 → 가장 명확한 한 표현을 남기고 나머지는 삭제. 단, 반복이 의도적 강조(예: "절대 X하지 마 — 재확인: X는 금지다")라면 유지. 판단이 모호하면 보존.

## AP-3: 무의미한 수식어 (Empty Adverbs)

### 왜 나쁜가
"매우 정확하게", "완벽하게", "최고로" 같은 수식어는 평가 기준 없이 품질만 과장한다. 모델은 이 단어를 받아도 무엇을 해야 할지 명확해지지 않는다. 측정 가능한 기준으로 바꿔야 실제 품질이 올라간다.

### Before
```
매우 정확하고 완벽한 번역을 해줘.
```

### After
```
번역 기준:
- 원문 의미를 누락·추가 없이 전달
- 자연스러운 목적 언어 표현 사용 (직역 금지)
- 전문 용어는 업계 표준 용어로 통일
- 모호한 원문은 가장 보편적 해석을 따르고, 주석으로 대안 명시
```

### 교정 원리
수식어가 구체적 기준으로 치환 가능하면 치환. 아니라면 삭제 (모호한 품질 요구 자체가 불필요). 도메인에 따라 다른 구체 기준이 있으면 그것을 사용.

---

## AP-4: 과도한 금지 나열 (Excessive Prohibitions)

### 왜 나쁜가
10개 이상의 "~하지 마"는 모델의 주의를 금지 회피에 분산시킨다. 인간도 그렇지만 모델도 "해야 할 것"을 아는 편이 훨씬 효과적이다. 금지가 긴 목록은 대개 "원하는 행동을 명시하지 못한 결과"의 그림자다.

### Before
```
- 이모지 쓰지 마
- 느낌표 쓰지 마
- "매우" 같은 부사 쓰지 마
- 반말 쓰지 마
- 영어 섞지 마
- 질문으로 끝내지 마
- 인사말 넣지 마
- 사족 달지 마
- 이유 설명하지 마
- 추측 표현 쓰지 마
- 불확실성 드러내지 마
```

### After
```
답변 스타일: 한국어 존댓말, 사실 기반 단정 서술.
- 본론 직답. 인사말·사족 없음.
- 불확실할 땐 "확인 필요"라고만 기재.
- 이모지·느낌표·부사 수식("매우", "정말") 사용하지 않음.
```

### 교정 원리
긍정 지시로 전환(무엇을 해야 하는지 명시) + 핵심 금지 3-5개만 유지. 유사 금지는 범주화하여 압축.

## AP-5: 목표 없는 역할 (Purposeless Persona)

### 왜 나쁜가
"당신은 X 전문가입니다"만으로는 행동이 정의되지 않는다. 모델이 역할을 연기하긴 하지만, 어떤 판단 기준·어떤 깊이·어떤 형식으로 답할지 알 수 없다. 역할은 "행동 기준"과 함께일 때 강력해진다.

### Before
```
당신은 10년차 보안 전문가입니다. 이 코드 봐주세요.
```

### After
```
당신은 10년차 애플리케이션 보안 엔지니어입니다. 아래 기준으로 코드를 검토합니다.

- OWASP Top 10 (2021) 기준 취약점 탐지
- 각 발견은 [severity/location/evidence/remediation] 4개 항목으로 기록
- Severity는 Critical/High/Medium/Low/Info
- 의심만 되는 경우 Confidence를 함께 기재
- 최종 요약에서 Critical/High를 먼저 배치
```

### 교정 원리
역할 정의 후 "그 역할이 수행할 구체적 행동 기준"을 반드시 이어 붙인다. 역할은 왜 존재하는가 — 판단 기준을 제공하기 위해서다.

## AP-6: 장황한 서두 (Buried Lede)

### 왜 나쁜가
모델은 primacy bias가 강해서 프롬프트 상단의 지시에 더 주의를 기울인다. 배경 설명이 먼저 나오고 실제 지시가 하단에 묻히면, 모델이 지시를 덜 중요하게 처리할 수 있다. "무엇을 해야 하는가"가 먼저, "왜·배경"은 별도 섹션으로.

### Before
```
우리 회사는 2010년에 설립된 핀테크 스타트업이고, 최근 B 라운드 투자를 받았으며, 주로 MZ 세대를 타겟으로 하는 간편송금 서비스를 제공하고 있습니다. 최근 경쟁이 심화되어 신규 기능을 빠르게 출시해야 하는 상황입니다. 이런 배경에서, 푸시 알림 카피를 작성해야 합니다. 신규 친구 초대 이벤트 알림이에요.
```

### After
```
<task>
신규 친구 초대 이벤트를 알리는 푸시 알림 카피 3개를 작성한다.
(각 40자 이내, 행동 유도 CTA 포함)
</task>

<context>
- 서비스: 간편송금 앱 (주 타겟: MZ 세대)
- 상황: 경쟁 심화로 신규 고객 획득 시급
- 회사 스테이지: B 라운드 투자 완료
</context>

<style>
친근한 반말 또는 캐주얼 존댓말. 이모지 1개 이내.
</style>
```

### 교정 원리
핵심 지시를 `<task>` 또는 상단 첫 줄에 선배치. 배경·이유는 `<context>`로 분리하여 참고 정보로만 기능하게 한다.

## AP-7: 암묵적 기대 (Implicit Expectations)

### 왜 나쁜가
사용자 머릿속에만 있는 출력 형식·길이·톤을 명시하지 않으면, 모델은 가장 흔한 형태로 답하고 사용자는 실망한다. "암묵지를 형식지로 꺼내는 것"이 프롬프트 설계의 핵심 중 하나다.

### Before
```
서비스 약관 초안 써줘
```

### After
```
서비스 약관 초안을 작성한다.

<scope>
- 서비스: {서비스명}
- 대상 국가: {대한민국 / 미국 / 기타}
- 주요 수익 모델: {SaaS 구독 / 광고 / 거래 수수료}
</scope>

<output_spec>
- 구조: 마크다운, 각 조항을 "제X조 [제목]" 형식으로 번호화
- 길이: 15-25개 조항
- 톤: 법률 문서체 (존댓말, 단정적 어조)
- 필수 포함 조항: 서비스 설명, 회원가입·해지, 개인정보, 금지행위, 책임 제한, 분쟁 해결, 부칙
- 법률 검토 필요 부분은 [법무 검토 필요] 태그로 표기
</output_spec>

<constraints>
- 실제 회사명·주소 등 구체 정보는 플레이스홀더로 둔다 ({회사명}, {주소}, {연락처})
- 지역별 법률 특이사항은 하단 주석으로 분리
</constraints>
```

### 교정 원리
출력 형식(마크다운 vs 일반 텍스트 vs JSON), 길이, 톤, 필수/선택 항목, 플레이스홀더 처리 방식을 명시한다. 모호 시 AskUserQuestion.

## AP-8: 과도한 MUST/NEVER (Authoritarian Overload)

### 왜 나쁜가
강압적 지시("반드시", "절대", "MUST", "NEVER")가 프롬프트 전반에 남발되면, 모델이 "뭐가 진짜 중요하지?"를 판단하기 어려워지고 전부 동일 강도로 취급하게 된다. 결과적으로 핵심 제약의 강제력이 약해진다. 또한 모델은 현명하므로 이유를 이해하면 훨씬 잘 따른다.

### Before
```
반드시 한국어로 답해야 한다. MUST.
답변은 절대 100자를 넘어서는 안 된다. NEVER.
반드시 숫자로 시작해야 한다. MUST.
절대 코드 블록을 쓰지 마라. NEVER.
반드시 마침표로 끝내야 한다. MUST.
```

### After
```
출력 규격:
- 언어: 한국어
- 길이: 100자 이내 (예산이 엄격함 — 초과 시 목록에서 제외됨)
- 시작: 숫자 1-9 중 하나로 시작 (후행 랭킹 시스템이 숫자로 파싱함)
- 형식: 일반 텍스트 (코드 블록은 스크립트가 처리하지 못함)
- 종결: 마침표 (문장 완결성 확인 용도)
```

### 교정 원리
강압적 지시 → **이유 설명**으로 전환. 모델이 규칙의 의도를 이해하면 엣지 케이스에서도 올바른 판단을 한다. 강조는 핵심 2-3개에만 집중하고, 나머지는 평범한 서술로 충분하다.

## 교정 판단 매트릭스

| 안티패턴 | 자동 교정 | 확인 후 교정 | 판단 경계 |
|---------|-----------|-------------|-----------|
| AP-1 모순 | ✅ (우선순위 추론 가능 시) | 양쪽이 모두 중요해 보일 때 | 둘 중 하나가 명백히 주 지시인가 |
| AP-2 중복 | ✅ | 반복이 의도적 강조로 보일 때 | 같은 지시인가 유사 지시인가 |
| AP-3 무의미 수식어 | ✅ | 도메인 특화 기준이 필요한 경우 | 맥락에서 기준 추론 가능한가 |
| AP-4 과도 금지 | ✅ | 금지가 도메인 규제·법률 요구일 때 | 금지가 순수 취향인가 규제인가 |
| AP-5 목표 없는 역할 | ✅ | 역할의 목적이 모호할 때 | 역할에서 행동 파생 가능한가 |
| AP-6 장황한 서두 | ✅ | 배경이 실제로는 제약일 때 | 배경과 지시의 구분이 명확한가 |
| AP-7 암묵적 기대 | ⚠️ | 대부분 확인 필요 | 합리적 기본값이 도메인 표준인가 |
| AP-8 과도 MUST/NEVER | ✅ | 규제·안전 요구일 때는 강조 유지 | 강조가 진짜 강제인가 습관인가 |

**⚠️ = AskUserQuestion 우선 고려**. AP-7은 형식·길이·톤 같은 암묵적 기대가 사용자 내부 정보인 경우가 많아 추측보다 확인이 안전하다.

---

## 교정 후 검증

모든 안티패턴 교정 후 아래 2가지를 재확인한다:

1. **의미가 보존되었는가** — 특히 AP-1(모순 해소), AP-4(금지 삭제), AP-8(강조 완화)은 의미 변화 위험이 크다. 원문이 "정말로 모순이었는지", "정말로 불필요한 금지였는지" 다시 생각.
2. **교정이 개선인가, 그냥 구조만 바뀐 변화인가** — 구조화를 위한 구조화는 가치가 없다. 모델이 실제로 더 잘 수행할 근거가 있어야 한다.
